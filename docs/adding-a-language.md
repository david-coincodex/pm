# Adding / maintaining a language

The frontend uses **next-intl**. UI strings live in one JSON file per locale under
`frontend/messages/` (`en.json` is the **source of truth**; every other locale is derived from
it). Translations are generated by `scripts/translate-messages.mjs` with GPT, using a per-key
context file so short labels translate with the right intent.

Two jobs, both required:

1. **Runtime wiring** — register the locale so routing/formatting work (light; next-intl does most
   of it automatically).
2. **Translations** — generate `frontend/messages/<loc>.json`.

> **Just changing a string on existing languages?** You only need the Translations tooling — jump to
> [Changing strings](#changing-strings-on-existing-languages).

Throughout, replace `<loc>` with the ISO code (e.g. `fr`). German (`de`) is the canonical reference.

---

## 1. Runtime wiring (only when adding a *new* language)

1. **`frontend/src/i18n/routing.ts`** — add `<loc>` to the `locales` array. This is the source of
   truth; the middleware (`src/middleware.ts`) and navigation helpers read it automatically.
   `localePrefix: 'as-needed'` means `en` is unprefixed (`/`) and other locales are prefixed
   (`/de/…`).
2. **`frontend/messages/<loc>.json`** — must exist with the endonym in the `language` namespace
   (e.g. `"language": { "de": "Deutsch", … }`). The translator creates the file for you in step 2;
   just confirm the endonym reads naturally afterwards.
3. **(Optional) Strapi content** — DB content (site/bundle/sale/blog/review copy) is a *separate*
   localization concern, out of scope for this UI tooling.

next-intl formats numbers/dates/currency via the `Intl` APIs keyed on the locale — no CLDR
registration needed (unlike Angular).

---

## 2. Translations

All commands run from `scripts/`. They read `OPENAI_API_KEY` from `scripts/.env` (or pass
`--token <key>`). Model defaults to `gpt-5.5` (override with `OPENAI_MODEL`).

### 2a. Refresh the context first

The translator feeds GPT a one-line annotation per key from `scripts/translation-context.json`
(English-keyed, language-independent). **Any new/renamed English key has no context until generated**,
which produces weaker translations — so always do this before translating.

```bash
node translation-context.mjs --check                 # how many keys lack context?
node translation-context.mjs --generate              # NEW KEYS ONLY: fill missing entries
node translation-context.mjs --generate --batch       # same, via Batch API (~50% cheaper)
node translation-context.mjs --check                 # confirm: 0 missing
```

The `--check` count must be ~0 before translating. (`--refresh [--scope <ns>] [--key <ns.key>]`
rewrites existing annotations.)

### 2b. Generate the locale file

Preview first, then translate:

```bash
node translate-messages.mjs --language <loc> --dry-run        # print, no write
node translate-messages.mjs --language <loc>                  # incremental: fill missing/empty keys
node translate-messages.mjs --language <loc> --fresh          # REWRITE everything from scratch
node translate-messages.mjs --language <loc> --batch          # Batch API (~50% cheaper, async)
```

Useful flags (compose freely):

```bash
--scope reviews                      # one top-level namespace only
--key pageSEO.discount.metaTitle,reviews.pros   # only specific key(s) (comma-separated)
--key reviews.pros --fresh           # rewrite just those key(s)
--skip-seo                           # translate everything EXCEPT the pageSEO namespace
--seo-only                           # translate ONLY the pageSEO namespace
--reorder                            # normalize key order + prune orphans to match en (no API calls)
--reorder --dry-run                  # preview the reorder/prune
```

`--batch` uploads all namespace chunks as one OpenAI Batch job, polls to completion, validates, then
writes. Failed/invalid chunks are retried synchronously (strict). For a handful of keys, omit
`--batch` (synchronous, immediate, slightly pricier).

### What is preserved automatically

Every file is written through one serializer: 2-space indent, literal Unicode, trailing newline,
**keys reordered to match `en.json` exactly**, and **orphan keys (not in English) removed**. A file is
only rewritten when its content changes.

The translator preserves and validates, per string:

- **Placeholders** `{name}`, `{count}`, … (next-intl single-brace).
- **ICU MessageFormat** — `{count, plural, one {# site} other {# sites}}`: the variable, the
  `plural`/`select` keyword, the category labels and `#` stay; only the inner text is translated.
- **HTML/markup tags** (for `t.rich`, if any).
- **Do-not-translate glossary** — `PornMode`, `Adult Time`, `LIVE`, `AI`, `VR` stay English even
  mid-sentence (`DO_NOT_TRANSLATE` in `translate-messages.mjs`).
- **Do-not-translate keys** — the `platform.*` payment-brand values (`visa`, `paypal`, `twint`, …) are
  copied verbatim from English; only `platform.sectionTitle/operatedBy/website/paymentMethods` are
  translated.

If a translated chunk changes any preserved token, it is retried (strict), then that namespace falls
back to English.

### Preferred translations (per language)

`scripts/translation-preferences.json` maps an English term to the team's chosen wording for a
locale (e.g. `{ "de": [{ "en": "deals", "preferred": "Angebote" }] }`). This is **soft guidance** —
the model still inflects the term to the right grammatical case. Add entries, then re-run
`--fresh` (optionally `--scope <ns>`) to apply.

### SEO strings

All SEO copy (meta titles/descriptions + on-page hero titles/subtitles) lives under the top-level
**`pageSEO`** namespace (`pageSEO.<page>.metaTitle | metaDescription | pageTitle | pageSubtitle`,
plus detail/fallback variants). Use `--skip-seo` to leave SEO untouched, or `--seo-only` to translate
just it.

## 3. Verify

```bash
# Key parity: every locale has the exact key set of English
node -e 'const f=s=>{const o=require(`../frontend/messages/${s}.json`);const k=(x,p="",a=[])=>{for(const n in x){const v=x[n],q=p?p+"."+n:n;v&&typeof v=="object"?k(v,q,a):a.push(q)}return a};return k(o).sort().join()};console.log("<loc>", f("en")===f("<loc>")?"OK":"MISMATCH")'
```

Then:

- **Build/typecheck** the frontend (`npx tsc --noEmit`) — next-intl throws on malformed ICU at
  runtime, so a clean `/<loc>/` render confirms the ICU survived.
- **Spot-check** `/<loc>/` pages (home, a discount page, reviews) in the browser: no raw keys leaking,
  placeholders resolved, and `platform.*` brands + `PornMode`/`LIVE` still English.

## Changing strings on existing languages

When you **add, rename, split, or remove a key**:

1. **Edit `frontend/messages/en.json`** (canonical key order). If a phrase must grammatically agree
   with an interpolated category (gender/case), prefer a **separate fully-spelled key per variant**
   over one template — one template can't inflect correctly in every language.
2. **Update code usages** of any renamed/removed key (grep `src/` for the old key).
3. **Update context** — new keys: `node translation-context.mjs --generate` (always generate, never
   hand-write — hand-written annotations drift in style). Removed/renamed keys: delete their entry by
   hand (the script does not prune orphans). Confirm `--check` is 0.
4. **Translate every locale** — a plain run fills new keys, reorders, and prunes the removed one:
   ```bash
   for loc in de; do node translate-messages.mjs --language "$loc"; done   # keep in sync with routing.ts locales (minus en)
   ```
   Add `--batch` for large changes; do **not** add `--fresh` unless you want to retranslate
   everything.
5. **Verify** (section 3).
